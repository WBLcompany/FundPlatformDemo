# البنية التقنية

ملخص قابل للتنفيذ من التصور التقني و HLD. أي قرار هنا يُعدَّل عبر `docs/decisions.md` لا بتجاوزه في الكود.

## ١. الستاك

| الطبقة | الاختيار |
| --- | --- |
| الواجهة والخادم | Next.js (App Router) و TypeScript strict |
| الواجهة العربية | Tailwind CSS بخصائص منطقية (`ms-*`, `me-*`, `ps-*`)، مكونات Radix/shadcn معاد تنسيقها بهوية وبل |
| التحقق | Zod: مخطط واحد للواجهة والخادم |
| النماذج القابلة للإعداد | JSON Schema مخزّن في نسخة الإطار، ومُرسِم نماذج واحد |
| قاعدة البيانات | Postgres عبر Supabase: RLS و Auth و Storage و Realtime |
| المهام والمؤقتات | pg_cron و pgmq (Supabase Queues) وعامل Node |
| المستندات | قوالب docx تُملأ (docxtemplater) ثم PDF عبر Gotenberg |
| فحص الملفات | ClamAV |
| الاختبارات | Vitest للوحدة، pgTAP للقاعدة والـ RLS، Playwright للمسارات الشاملة، axe للوصولية |
| الرصد | OpenTelemetry (واتفاقيات GenAI لاستدعاءات مانح) و Sentry |
| الأدوات | pnpm workspaces، Turborepo، ESLint بقواعد حدود الوحدات، Prettier |

## ٢. الشكل العام

Modular monolith من حاويتين: **تطبيق الويب** و**العامل الخلفي**، يتشاركان طبقة النطاق نفسها. فوق Postgres واحد بـ schema لكل وحدة.

```
apps/
  web/            Next.js
    app/(staff)/        بوابة موظفي المانح
    app/(association)/  بوابة الجمعيات
    app/(supplier)/     بوابة المورّدين
    app/(operator)/     لوحة مشغّل وبل (نطاق فرعي منفصل)
    app/(public)/       صفحات البرامج العامة
    app/api/v1/         Public API (قراءة)
    app/api/hooks/      webhooks واردة (مانح، الرسائل)
  worker/         معالجات outbox والمؤقتات ومهام مانح والمستندات
  prototype/      نموذج Figma القابل للنقر (بيانات وهمية، مرحلة التصميم فقط)
packages/
  domain/         وحدة لكل سياق، بلا تبعية لإطار عمل
  rules/          مقيّم جداول القرار (دالة نقية)
  kernel/         audit, events, notifications, files, entity-refs, search, reporting
  adapters/       entities, manih, otp, email, whatsapp, storage, docgen, av
  ui/             مكونات وبل، قالب صفحة العنصر، مكونات الذكاء، مُرسِم النماذج
  tokens/         رموز التصميم (مصدر واحد لـ Tailwind و Figma)
supabase/
  migrations/     schema لكل وحدة، RLS، triggers السجل
  tests/          pgTAP: العزل ومصفوفة الصلاحيات
  seed/           بيانات تجريبية لمانح «الملاحي-تجريبي»
evals/            مجموعة تقييم مانح وعتباتها
```

## ٤. الثوابت (invariants)

هذه تُفرض في الكود وقاعدة البيانات معاً، وتُختبر في كل دمج:

1. **tenant_id** في كل جدول أعمال، ومفاتيح أجنبية مركّبة (tenant_id, id)، وRLS بالرفض الافتراضي. المانح يُحدَّد من JWT لا من الطلب.
2. **الكتابة عبر الخادم فقط:** Server Action → Zod → `can()` → آلة الحالة → معاملة واحدة.
3. **المعاملة الواحدة** تكتب: تغيير الحالة، وقيد السجل، وحدث outbox، وموعد المهلة. مع تحقق `version` (optimistic concurrency).
4. **سجل التدقيق** إلحاقي فقط: REVOKE لـ UPDATE/DELETE، و trigger يرفض، و hash chain لكل مانح، وجذر يومي إلى تخزين WORM.
5. **إطار المنح المنسّخ:** الاعتماد يجمّد المسودة في لقطة JSON. كل طلب مثبّت على نسخة تقديمه، وكل قرار مختوم برقمها.
6. **المال:** أعداد صحيحة بالهللة (bigint). الاعتماد النهائي يحجز المبلغ بمعاملة تقفل صف الرصيد. الأرصدة تُحسب من دفتر حركات لا يُعدَّل.
7. **التواريخ:** timestamptz بـ UTC، والعرض بتوقيت الرياض وبالتقويمين.
8. **لا محرك سير عمل حر:** ست آلات حالة ثابتة (الطلب، المشروع، التسليم، أمر الصرف، طلب التعديل، أمر المورّد) ومحرك اعتماد واحد.
9. **الذكاء لا يغيّر حالة:** مخرجات مانح سجلات `ai_output`، والانتقال يتطلب إجراء إنسان.
10. **service_role** لا يُستخدم في كود التطبيق.

## ٥. آلة حالة الطلب

```
draft → submitted → in_review ⇄ awaiting_info
                    in_review → in_approval → approved → agreement → project
                    in_approval → in_review   (إعادة بملاحظات)
                    in_approval → rejected
                    submitted/in_review → withdrawn (من الجمعية قبل القرار)
```

كل دخول لحالة يحسب `due_at` بأيام العمل (الأحد–الخميس) وتقويم إجازات المانح. مهمة pg_cron تلتقط المتجاوز وتطلق `sla.breached`.

## ٦. محرك الاعتماد الواحد

يستقبل «موضوع اعتماد» (منحة، أمر صرف، طلب تعديل) بخصائصه. يقيّم جدول التفعيل من نسخة الإطار، ويجمّد السلسلة المنطبقة، ويفتح المستوى الأول. الإجراءات: اعتماد، رفض، إعادة، تعديل المبلغ (يعيد تقييم الجدول وقد يضيف مستوى). مستوى اللجنة يقبل إدخالاً جماعياً من محضر واحد.

## ٨. الأمن

- MFA (TOTP) لموظفي المانح، وجلسات بمهلة خمول.
- step-up برمز تحقق للتغييرات الحساسة: الحساب البنكي، البريد الرسمي، صلاحيات الجمعية، صاحب الصلاحية.
- مفتاح بيانات لكل مانح (envelope encryption) للحقول المقيدة والملفات، ليمكن الإتلاف الموثق.
- الملفات: منطقة حجر → ClamAV → مسار المانح، وتُقدَّم من نطاق منفصل بـ `Content-Disposition: attachment`.
- CSP صارمة، وحد معدل على الدخول والرموز والبحث والسؤال.
- خروج الشبكة عبر وكيل بقائمة وجهات مسموحة. Gotenberg و ClamAV بلا خروج.

## ٩. النشر

Kubernetes عند مزود سحابي محلي مرخص، منطقتا توافر، Postgres مُدار (يُحسم في Q-1). ثلاث بيئات: تطوير، تجهيز ببيانات مصطنعة، إنتاج. ترحيلات متوافقة للخلف (expand ثم contract). لا بيانات حقيقية خارج الإنتاج.

## ١٠. بوابات الدمج

1. lint وحدود الوحدات و typecheck.
2. Vitest للنطاق وجداول القرار وآلات الحالة.
3. pgTAP: اختبار العزل العدائي، ومصفوفة الصلاحيات، وثوابت السجل والمال.
4. Playwright: الدورة الكاملة مرتين، بالذكاء (محوّل مانح وهمي) ومعطّلاً.
5. axe على الشاشات الأساسية.
6. SAST وفحص التبعيات.
